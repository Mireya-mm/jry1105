## 0. 文档定位

本方案不重复描述"发现了什么"，而是回答"如何用工程化手段把发现转化为可落地的能力"。
它建立在前期发现工作的证据之上，给出一套以 **LLM 多智能体 Harness** 为核心的技术解决方案，
并明确设计哲学、架构、关键决策、评测与路线图。所有提示词规格另见 `提示词.md`。

---

## 1. 问题重述：从"现象"到"定义"

前期调研已用多源证据（访谈、现场观察、流程走查）印证了三个系统性问题：

- **H1 审批串行**：合同需经 4 个串行节点，平均耗时约 5 天，卡点集中在法务环节。
- **H2 模板分散**：合同模板散落于个人盘与共享盘，缺乏统一模板库，重复起草成本高。
- **Q3 归档检索难**：签署后无统一检索入口，客户难以找回历史合同，体验受损。

**本质抽象**：这三类问题的共同根因是——*业务知识未被结构化、流程决策缺乏数据支撑、跨系统信息未打通*。
因此，技术方案的目标不是"再建一个系统"，而是"为业务装上可解释的认知与协作能力"。

---

## 2. 设计哲学（第一性原理）

在引入任何模型之前，先确立五条不可妥协的原则，它们决定了后续所有技术取舍：

1. **人机协同，而非替代**：LLM 是"思考放大器"与"初稿生成器"，关键决策（如对外承诺、方案拍板）保留人类审批。
   *理由*：合同业务具备法律与商业后果，纯自动决策的风险不可接受。
2. **可解释优先**：任何一条结论都必须能回溯到证据（某段访谈、某条日志、某份制度）。
   *理由*：可追溯性是可被信任、可被审计、可被持续改进的前提。
3. **隐私与合规内建（Privacy-by-Design）**：合同数据属高敏感，须默认脱敏、最小化采集、全程审计、不出域。
4. **渐进自动化**：能力按"辅助 → 建议 → 半自动 → 自动"分级释放，每一级以评测指标为放行门槛，而非一次性全开。
5. **评测驱动迭代**：用可量化指标替代主观感觉衡量效果，建立离线评测集与回归测试，杜绝"感觉变好了"。

## 3. 总体架构：FDE Discovery Harness

**Harness（编排框架）** 是本案的核心抽象：它负责把多个专职 Agent、工具（检索/代码/数据库）、
记忆（向量库）与评测串成一个可复用、可观测、可灰度的工作流。整体分四层：

```text
[接入层]  合同系统 / 审批日志 / 访谈录音 / 模板库
          → 统一数据接入、清洗、脱敏、结构化
                ↓
[认知层]  多专职 Agent：
          业务挖掘 / 访谈分析 / 现场调研 / 根因诊断 / 方案生成 / 流程图生成
                ↓
[编排层 Harness]  工作流编排 + 状态管理 + 工具调用
                  + 人在回路(HITL) + 评测闭环(LLM-as-Judge)
                ↓
[应用层]  发现报告 / 现状-目标流程图 / 改进建议 / 可视化看板
```

各层之间以 **JSON Schema 固化的接口** 通信，保证组件可替换、行为可观测、故障可定位。

---

## 4. 核心能力映射到 FDE 三段式

本方案沿用 `README.md` 定义的 FDE 方法论，将每一段映射为具体技术能力：

- **Find（发现）**
  - *业务挖掘 Agent*：从资料、指标、日志中自动识别问题与机会，输出带假设编号的清单。
  - *访谈分析 Agent*：将访谈录音/文本转化为结构化洞察，并反向标注其支撑的假设（H1/H2/Q3）。
- **Diagnose（诊断）**
  - *根因诊断 Agent*：用 5-Why + 数据交叉验证，定位 H1/H2 的真实根因并量化影响。
  - *现场调研 Agent*：补全证据缺口，对假设做"支持/削弱/无关"的判定。
- **Enable（赋能）**
  - *方案生成 Agent*：基于诊断给出可落地方案（并行审批、中央模板库、统一检索入口等）。
  - *流程图生成*：输出 Mermaid 现状/目标流程图，供业务方直观评审。

## 5. 关键技术决策与权衡（工程判断力）

本节是方案"深度"所在——不只给结论，更给**为什么**。

### 5.1 多 Agent 还是单一巨型 Prompt？
**选择多 Agent。** 理由：模块化带来可审计、可独立评测、可灰度替换；单一 Prompt 难以约束输出、
易超出上下文、不可维护。代价是编排复杂度，由 Harness 统一承担。

### 5.2 RAG 还是微调（Fine-tuning）？
**合同模板与制度知识用 RAG（检索增强），不微调。** 理由：
- 避免把高敏感语料固化进模型权重，降低合规风险；
- 知识可热更新（制度一改，检索即变），无需重训；
- 仅当领域术语识别明显不足时，才考虑参数高效微调（LoRA），且须先脱敏。

### 5.3 确定性输出
所有 Agent 输出强制 **JSON Schema 校验**（如访谈洞察含 `hypothesis_id`、`evidence`、`confidence`），
下游系统可直接消费，避免"自然语言不可解析"的工程灾难。

### 5.4 人在回路（HITL）
在"方案生成""对外承诺"节点**强制人工确认**；其余节点用 LLM-as-Judge 自动校验 + 抽样人工复核，
在自动化与可控之间取得平衡。

### 5.5 评测双轨
- **规则校验**：Schema 合法性、必填项、引用证据是否存在；
- **LLM-as-Judge**：评估相关性、可操作性、合规性。
双轨互补，避免单一方法带来的系统性偏差。

## 6. 提示词工程策略（详见 `提示词.md`）

采用 **ROCF 框架**：**R**ole（角色） / **C**ontext（上下文） / **C**onstraint（约束） / **F**ormat（格式）+ Task。
关键技巧：

- **思维链（CoT）** 用于根因诊断，迫使模型显式推理；
- **自洽（Self-Consistency）** 用于关键判断，多采样后投票；
- **少样本（few-shot）** 用于结构化抽取，稳定输出格式；
- **自我批判（Self-Critique）** 作为质量闸门，未通过则重写；
- **版本化与回归**：每个 Prompt 入版本库，配套评测用例，改动须通过回归。

---

## 7. 数据、隐私与合规

合同数据的高敏感性决定了合规不是"附加项"，而是架构的**地基**：

- **数据分级**：合同正文=高敏感；流程元数据=中；公开制度=低。
- **脱敏流水线**：PII 识别 → 掩码 → 映射表加密存储（仅授权角色可还原）。
- **不出域**：推理在私有化/受控环境进行，禁止合同正文外发至公有模型。
- **审计留痕**：所有 Agent 调用记录"谁 / 何时 / 输入摘要 / 输出 / 依据证据"。
- **合规对齐**：符合《个人信息保护法》《数据安全法》及行业合同管理规范。

---

## 8. 评估体系

方案价值必须用指标证明，而非叙述：

| 指标 | 定义 | 目标 |
| --- | --- | --- |
| 发现覆盖率 | 已知问题被 Agent 识别的比例 | ≥ 90% |
| 建议采纳率 | 人工采纳的方案占比 | 持续提升 |
| 流程图准确率 | Mermaid 与真实流程一致性（人工抽检） | ≥ 95% |
| 人工修正量 | 每千字输出需人工修改字数 | 越低越好 |
| 合规红线命中 | 输出触发隐私/合规红线的次数 | 0 |

建立**离线评测集**（历史真实案例匿名化），每次 Prompt 或模型变更均跑回归。

---

## 9. 实施路线图

- **P0（1–2 周）**：数据接入 + 脱敏流水线 + 离线评测集 + Harness 骨架。
- **P1（2–4 周）**：单 Agent（访谈分析）端到端跑通 + 人在回路。
- **P2（4–8 周）**：多 Agent Harness，打通 FDE 三段闭环。
- **P3（8 周+）**：灰度上线，指标达标后逐步释放更高自动化等级。

---

## 10. 风险与缓解

- **幻觉**：JSON Schema 校验 + 引用约束 + LLM-Judge + 人工抽检。
- **数据泄露**：不出域 + 脱敏 + 审计留痕。
- **过度依赖**：保留人工决策权，且具备"一键降级到纯人工流程"的能力。
- **可维护性**：Prompt 版本化、评测回归、文档化、接口 Schema 固化。

---

## 11. 结论

以"**人机协同、可解释、合规内建、评测驱动**"为基石，用 Harness 把原本分散的发现能力工程化，
使合同业务的发现与优化从"经验驱动"走向"证据驱动"。建议以 P0 脚手架为起点快速验证，
用评测数据决定何时、以何种等级释放自动化能力。
